## Production Audit — Nails by Kristina

Цель: пройти проект сверху вниз, найти баги/риски, и применить только минимальные безопасные правки. UI, бизнес-логика и архитектура остаются прежними.

### Этап 1 — Audit (только чтение, без правок)

1. **Frontend / React**
   - `App.tsx`, `main.tsx`, провайдеры (`AuthContext`, `SideMenuContext`), роутинг — проверка порядка провайдеров, persister (использование `persister!`), guard'ов маршрутов, fallback `NotFound` для неавторизованных.
   - Все страницы в `src/pages/*` и подпапке `settings/` — проверка на: бесконечные ре-рендеры, отсутствующие deps в `useEffect`/`useMemo`/`useCallback`, утечки подписок Supabase realtime, ключи в списках, условный вызов хуков, `dangerouslySetInnerHTML`.
   - Хуки в `src/hooks/*` (особенно `useAppointments`, `useClients`, `useVisits`, `useTimerSessions`, `usePhotos`) — корректность query keys, инвалидации, optimistic updates, race-conditions, error states.
   - UI-компоненты (`ClientPicker`, `TimePicker`, `BottomSheet` и др.) — проверка cleanup'ов слушателей, портала, focus trap, утечек памяти.

2. **Backend / Supabase**
   - Сверка таблиц и enums со схемой, RLS-полиси на полноту (insert/update/delete с `owner_id`), отсутствие FK (есть риск orphan-записей — отметить, не править если ломает миграции).
   - Storage buckets (`visit-photos` private, `master-avatars` public) — проверить, что upload пути и удаление файлов соответствуют RLS политикам storage.objects.
   - Auth: HIBP уже включён; проверить, что нигде нет `signInAnonymously`, что обработка `onAuthStateChange` не вызывает Supabase-методы синхронно внутри callback.
   - `supabase/config.toml` — без правок project-level настроек.

3. **Security / валидация**
   - Поиск использования `localStorage`/`sessionStorage` для критических флагов, hardcoded secrets, логирования PII (телефоны клиентов, email).
   - Валидация форм (zod) на ключевых формах: запись, клиент, расход, доход, профиль.
   - Запуск `security--run_security_scan` и `supabase--linter` для подтверждения.

4. **Performance / стабильность**
   - Тяжёлые списки без виртуализации (Clients, Gallery) — только отметить, без рефактора.
   - Картинки без `loading="lazy"` и `alt`.
   - Использование `framer-motion` в больших списках (риск jank).
   - Console errors/network errors через `code--read_console_logs` и `code--read_network_requests`.

5. **Качество кода**
   - Поиск unused imports/exports, dead files, дубликатов утилит, `// TODO`/`FIXME`, `any` в критических местах.
   - Несогласованные форматы дат/денег (UZS) между страницами.

Итог этапа 1 — отчёт со списком находок, разбитых по severity: **Critical / High / Medium / Low / Cleanup**.

### Этап 2 — Critical issues list

Из аудита выделяю только то, что:
- ломает прод (runtime/crash, утечки данных, RLS-обход),
- ломает UX молча (нет error state, бесконечный спиннер, потеря данных при оффлайне),
- security-риски с реальным impact.

Каждый пункт: файл:строка → симптом → почему критично → минимальный fix.

### Этап 3 — Минимальные безопасные правки

Правила:
- Один fix = один логический коммит.
- Никаких рефакторов «по дороге», переименований, перестановок компонентов.
- Не трогаю UI/UX, бизнес-логику, цвета, тексты — только если это и есть баг.
- Никаких новых зависимостей (zod уже есть — можно использовать).
- Миграции БД — только аддитивные (новые policies/grants), без drop/alter существующих таблиц.

### Этап 4 — Regression testing после каждого fix

Для каждой правки:
- сборка проекта (автоматическая в харнессе),
- если затронут UI/flow — открыть превью через browser-инструменты и пройти затронутый сценарий (auth → создание записи → клиент → визит → финансы),
- проверить console + network на ошибки,
- проверить, что соседние страницы не сломались.

### Этап 5 — Финальный отчёт

- Что найдено (по severity).
- Что исправлено и как.
- Что сознательно НЕ тронуто и почему (риск/scope).
- Открытые рекомендации для будущих итераций (без авто-применения).

### Технические заметки

- Не редактирую: `src/integrations/supabase/client.ts`, `src/integrations/supabase/types.ts`, `.env`, project-level `config.toml`.
- Любые `CREATE TABLE` в миграциях (если понадобятся) сопровождаются `GRANT` + RLS по правилам проекта.
- Roles/admin-флаги — только через `user_roles` + `has_role()` (сейчас в проекте ролей нет, новых не ввожу без запроса).
- Memory-правила проекта (бренд, палитра, нижняя навигация) соблюдаются.
